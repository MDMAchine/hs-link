# Developing HOT-STEP LINK

---

## Architecture

The plugin has three threads and a pool:

**Audio thread** (real-time). Reads the host playhead and writes the sync snapshot (`HostSyncState`) through atomics. Pushes incoming audio into the lock-free SPSC ring (`CaptureEngine`). Renders the active audition take into the output buffer via `AuditionEngine::render`, which does no allocation and takes no locks.

**DawWorker** (`juce::Thread`). Owns all HTTP. Runs the heartbeat loop, submits and polls jobs, downloads take audio into temp files, and publishes job state through a mutex-guarded list. Never touches the audio thread or the message thread directly; UI reads snapshots.

**Decode pool** (`juce::ThreadPool`, 1 thread). Loads and resamples take WAVs in the background when a take is selected for audition. Publishes the decoded buffer through an atomic pointer swap (`AuditionEngine`). The audio thread picks up the new pointer on its next block; retired pointers are freed by the message thread after the audio thread has finished two blocks with the new pointer.

**Message / UI thread.** Drives the JUCE editor on a VBlank timer (`VBlankAttachment`). Polls `DawWorker::getJobs()` and `AuditionEngine::collectGarbage()` each tick. Calls `HotStepLinkProcessor::pollCapture()` to finalise a finished capture into the source file.

### Lock-free rules

- The audio thread only writes atomics and pushes to the SPSC ring. It never calls `new`, takes a mutex, or calls into the DawWorker.
- The DawWorker never writes to `HostSyncState` or the capture ring.
- `AuditionEngine::render` uses an atomic pointer load to get the current take, reads from the take buffer (immutable once published), and bumps a block counter. No mutex is taken in the audio path.
- The only mutex in `AuditionEngine` is `ownLock`, taken only by the message thread for GC.

## Generation queue design

The queue lives entirely inside `DawWorker`, in the `jobs` vector (`source/PluginProcessor.h`, `source/PluginProcessor.cpp`). The audio thread never touches it.

**Thread and lock.** All reads and writes to `jobs` go through `DawWorker::lock` (a `std::mutex`). The only exception is `getJobs()`, which takes the lock, copies the vector, and returns the copy so the message thread can read a consistent snapshot without holding the lock.

**FIFO ordering.** `submitGenerate` appends a new `DawJob` with `state = pending` to `jobs`. In `processJobs`, before dispatching a pending generate job, the worker checks whether any earlier generate job is still in flight (not finished and not waiting, see `isWaiting`). If one is, the pending job is skipped on that pass. This gives strict FIFO ordering with one job in flight at a time.

**Submit window.** The submit POST runs on a copy of the job with the lock released, and can take seconds (source upload, busy server; `kSubmitTimeoutMs` is 120 s). When `processJobs` picks a pending job it sets `DawJob::submitting` on the entry in `jobs`, under the lock, before releasing it. The state stays `pending` until the POST returns, but `isWaiting` is false while `submitting` is set, so the job counts as the one in flight: `removeQueued` returns false for it, the card shows `sending` with no `x`, and no other job is dispatched. `cancelJob` only sets `cancelRequested` on the entry; the publish step after `stepJob` merges it into the returned copy, and the next pass sends the cancel for the server id and polls, as for any running job. A failed POST ends the job as `failed`. The flag is cleared when the result is published.

**Backend switch before the submit.** Inside the submit window, before the POST, `DawWorker::ensureBackend` runs for a generate job whose `expectedBackend` is not empty. It asks `GET /api/backends` (HOT-Step's main API, not the facade; no auth, the `X-DAW-Key` header is sent anyway) and, when `activeId` is another backend, sends `POST /api/backends/active` with `{ "id": "<backend>" }`. The server answers at once (a settings write; the outgoing backend's memory is freed in the background and the job's own runner waits for that), so `kSwitchTimeoutMs` (10 s) only bounds a server that does not answer. The listed entry carries `DawJob::switchingTo` (the display name) from before the GET until the POST has answered, which the editor shows in the status pill, the job line and the queue row; `cancelJob` cancels the request in flight (the GET or the POST) when it is set. It is set before the GET so the row reads queued, switching, sending, running and never `sending` before `switching`; `ensureBackend` clears it on every return. Side effect: a job whose backend is already active, or whose server has no backend list, also reads `switching` / `Switching to <backend>...` for the GET round trip, although no switch POST is sent. A job found cancelled before the GET sends no GET. A GET that is not a 200 with an `activeId` (older server, the contract stub's 404, no answer) skips the switch and the submit goes as before. A failed switch (no answer, 404, any other code, or a 200 that names another backend) ends the job as `failed` with `switchFailText` and cancels every waiting job with the same `expectedBackend` under the lock, each with a `Not sent` reason and a `finishSeq` below the failed job's. They are cancelled and not held, because a held job could only go on by a retry that nobody asked for. Nothing calls `ensureBackend` outside a queued job. The server has no reply that means "busy" for a switch today; 409, 423, 429 and 503 are worded as busy in case it gets one. Hooks: `switchBackend` (false = no question, no switch), `testBackendCall` (a function that stands in for both requests), `switchesSent`, `getSwitchingTo()`, and the pure `switchFailText` and `backendLabel`.

**Orphan guard.** If the publish step finds no entry in `jobs` for a generate result that carries a server job id and is not terminal, the worker sends a cancel for that id (lock not held), writes a line through `juce::Logger`, stores the id (`getLastOrphanId`) and increments `orphansCancelled`. With the submit mark in place no code path removes a job in that window; the guard is there so a server job can never be left without a local owner.

**Limits and their constants (PluginProcessor.h):**
- `DawWorker::kMaxQueued = 8`: maximum number of generate jobs allowed in `pending` state at once. `submitGenerate` counts non-cancelled pending jobs; if the count is already 8, it returns 0 (rejected).
- `DawWorker::kKeepFinished = 8`: maximum number of finished generate job cards kept in `jobs`. `pruneFinishedLocked` removes cards until at most 8 remain, in this order: first failed or cancelled jobs with no takes, oldest first (oldest = lowest index), skipping the job that finished most recently so the error of the job that just ended stays readable; then the oldest finished jobs. "Finished most recently" is the highest `DawJob::finishSeq`: a counter under the worker lock stamps each job when its finished state is published in `processJobs` (and `pruneFinishedLocked` stamps any finished job that has no stamp yet), so the exemption follows finish order, not list position. A waiting job that is cancelled after the running job was submitted sits later in the list but does not take the exemption from a job that finishes after it. Only finished jobs are erased; a waiting, sending, running or still downloading job is never pruned. Because that one card is skipped, a run of failures can cost at most one card that has takes. The `pruneTakelessFirst` test hook switches the first pass off; the `finishSeqRule` test hook restores the old rule (the last finished card in the list is the exempt one).

**When pruning happens.** `pruneFinishedLocked` is called at two points in `processJobs`: once at the top of the loop (on every pass) and once immediately after a job reaches a terminal state, so the cap is enforced as soon as a job finishes rather than waiting for the next pass. This is controlled by the `pruneOnFinish` test hook.

**Takes outlive job cards.** Pruning drops job cards only. Takes are owned by `HotStepLinkProcessor::takes` (a vector of `TakeEntry`: job id, take index, temp file, lasting file, lasting name), guarded by `takesLock` and never touched by the audio thread. `DawWorker::stepJob` calls `onTakeDownloaded` on the worker thread right after each take's download completes; the processor's `registerTake` appends the entry as unsaved, publishes the download and then copies the file into the stable session folder (`copyStable`, outside `takesLock`); the order is given under "Take names and the order of a download" below. This happens before the job is published as finished, so a lasting copy exists before the card can be pruned, with or without an editor. The editor's `refreshTakes` builds the grid from `getTakes()` and filters by `TakeEntry::jobId` when a queue card is selected. `getTakes()` only copies the list; it does no disk IO. `stableTakeFor` remains for callers that hold a `DawJob`.

**Take names and the order of a download.** A take's file name is `<caption-slug>_<backend>_t<n>_<bpm>bpm_<6 hex>.wav` (`StableTakes::makeTakeName`: `makeName` plus a take id from `ExclusiveFile::uniqueToken (6)`), for example `m2_first_auto_t1_0bpm_f49f31.wav`. `DawWorker::stepJob` picks it once per take (`DawWorker::takeFileName`) and it is the same string in the temp session folder, in the lasting folder, in a `recovered_` folder, in the marker line and as the star key (`TakeEntry::name` is the temp file's name). Two takes of one prompt differ by the id, so `copyUnique`'s `name_2` loop is only a backstop. Order on the worker thread: (1) the bytes are downloaded to `<name>.part` in the temp session folder (`DawWorker::partFileFor`); a failed or incomplete download deletes its `.part` and never makes a `.wav`, while a download that ran to its end is recorded even when the worker's exit is signalled right after it; (2) `onTakeDownloaded` calls `registerTake`, which builds the `TakeEntry` from the job without opening the file and adds it with an empty `stable` under `takesLock`; (3) the duration is read from the file outside the lock (`readTakeDuration`); (4) `DawWorker::publishDownload` renames the `.part` to the take name with `ExclusiveFile::moveNoReplace`, up to 6 tries; when the rename keeps failing the take stays recorded with the `.part` as its temp file (see "Takes in a `.part` file"); (5) `registerTake` wakes the saver thread (`wakeSaverForNewTake`: `TakeSaver::takeRecorded` sets a flag and calls `notify()`) and returns. The worker makes no lasting copy and no file call outside the temp session folder. On the saver thread: (7) `ensureStableCopies (true)` calls `copyStable` for every take whose copy was never attempted; (8) `stable` is set on the entry, found by its temp file, a `saved.log` line is written (`noteSaved`). First copies and retries are the same code. While the plugin is closing `registerTake` still runs (1) to (5); the saver starts no copy then, so the take stays unsaved. A worker without a callback (tests) does the rename itself after (1). The adoption pass never copies a capture (`source_<digits>.wav`), and it copies a `.part` only when `DawWorker::isTakePart` accepts it.

**One temp folder per instance.** The constructor points the worker's takes folder at `<temp root>/<tempSessionName>`, the folder the captures (`source_<n>.wav`) already used; `tempSessionName` is `session_<date>_<time>_<6 hex>` and always has the token. `getOwnTempFolders` therefore returns one folder unless a test calls `setTakesFolder`. A bare `DawWorker` defaults to `session_<milliseconds>_<6 hex>`.

**Takes that cannot be saved.** Every entry with an empty `stable` is waiting for its first copy attempt. `TakeEntry::copyFailed` is set only when a lasting-copy attempt for that take has actually failed (in `ensureStableCopies`, on the saver thread), and cleared when a copy succeeds; an aborted copy (plugin closing) does not set it. The notice count of `getSaveNotice()`, the NOT SAVED badge, the one `juce::Logger` line (the retries do not log) and the restart of the retry schedule depend on `copyFailed`, so a take that is between its record and its first copy shows none of them. There is no `copyPending` flag any more: only the saver thread copies, so an entry with an empty `stable` and `copyFailed` false is simply waiting for its first attempt. The grid shows a take with an empty `stable` by its temp file; audition, star and Export WAV work on it, and `TakeCell::mouseDrag` refuses the drag and paints the reason (failed or not copied yet), so a temp path is never handed to the host. A star is keyed by the take's file name, which is the same before and after the save, so nothing moves it. Stars saved by an earlier build (keyed by an id-less name) still load and match a listed take of that name. `getSaveNotice()` (no disk IO) gives the count, the lasting folder, the temp folder and what was recovered; the editor shows its text in its own label under the Takes grid, with a Retry save button that calls `requestSaveRetry()`.

- Adoption model (take store). A crashed or closed-with-unsaved-takes session folder is not rescued by a separate copy pass any more: `HotStepLinkProcessor::adoptDeadFolders` (saver thread, at its start and on `requestSaveRetry()`) adopts it into the ordinary take list. The steps:
  - owner.lock takeover: for every `session_*` folder under the temp root that is not this instance's own and not a live lockless folder, `tryAcquireExisting` is tried on its `owner.lock`. `Held` proves the owner is dead; the lock is kept (in `adoptedLocks`) for everything done to that folder until it is removed or the plugin closes. `Busy` = alive: skipped whole and counted in `rescueLockedSkips`. `Failed`: left alone.
  - recovered_<session>: every take found becomes a `TakeEntry` with `adopted` set and `destFolder = <lasting root>/recovered_<session folder name>/`. The saver then copies it like any other take (same exclusive copy, same size check, same retry on failure). The temp originals are not touched until the folder is removed. Candidates: the lines of a legacy marker (read only), then (with `protectByDefault`) every non-capture `*.wav` directly in the folder and every complete `*.wav.part` (`DawWorker::isTakePart`), under its `.wav` name. A zero-byte file is skipped and logged (`zeroByteSkips`); it is not a take.
  - saved.log proof: a candidate whose name (or relative path) and byte size already have a `saved.log` line is not adopted; it is proven saved. After an adopted take's copy, `noteSaved` appends its line, so the proof is the same for takes of the owner and adopted takes.
  - Keep guard (`keepGuard`, W1 and W2): `finishAdoptedFolders` removes an adopted folder (with `removeLockedFolder`, under its held lock) only when no adopted take of it is pending and `adoptedFolderSafeToRemove` is true. That is the allowed-file set: `owner.lock`, `saved.log`, the legacy marker (`isBookkeepingName`), a capture (`source_<digits>.wav`), a zero-byte file, the `Deleted` folder, and a `*.wav` or `*.wav.part` that `saved.log` proves saved under its own or its `.wav` name with its size. Any other file or subfolder keeps the folder. A scan that stopped early or did not sweep puts the folder in `adoptedKeepWhole`, which keeps it whole. A kept folder stays held until close. One `juce::Logger` line names a kept folder and its first blocking entry (`keptFolderCheck`, from `adoptedFolderBlocker`), once per folder per process, not on every pass.
  - Legacy folder path: a folder without `owner.lock` (an older build, or a lockless instance that died) cannot prove a dead owner. It is adopted at once when it has a legacy marker (`hslink_unsaved.txt`, header `HSLINK-UNSAVED v1`, read only, never written by this build), otherwise only once its newest content is older than 24 h (`DawWorker::staleAgeMs`). One instance per process claims it (`legacyClaims`). When its takes are saved only its marker is deleted; the folder ages out by `saved.log`. A marker with an unknown header, one that cannot be opened, or one with a path that leaves the folder is not adopted and not changed.
- Session lock: `ExclusiveFile::SessionLock` (ExclusiveFile.h/.cpp). `tryAcquire (folder)` creates or opens `<folder>/owner.lock` and keeps it open: on Windows `CreateFileW` with read and write access, `FILE_SHARE_READ` only and `OPEN_ALWAYS`; elsewhere `open` plus `flock (LOCK_EX | LOCK_NB)`. A second `tryAcquire` on the same folder, from another instance in the process or from another process, returns `Busy` (Windows: sharing violation) while the first is held. The operating system drops the hold when the process ends. Results: `Held`, `Busy` (someone alive holds it), `Failed` (the file could not be created or opened). Staleness rule: a lock is stale exactly when it can be acquired; there is no time, pid or heartbeat check, and an `owner.lock` file left by a dead process is only a file that anyone can open and lock. While the lock is held on Windows the lock file itself cannot be deleted, so `HotStepLinkProcessor::removeLockedFolder` deletes everything else, releases the lock and then removes the file and the folder; a folder delete that fails is tried again at a later start.
- Owner side: the constructor creates the temp session folder and acquires its lock (`ownLock`); on `Busy` it picks another token, up to 4 names, then a fifth that it does not lock. If the lock cannot be made (`Failed`), the instance runs without one, one log line is written per process, and the instance is a lockless instance (see below). The destructor releases the lock after it has kept or deleted the folder.
- `saved.log`: a text file in the temp session folder, append-only, one line per take file of that folder whose lasting copy was made: `<take file name><TAB><byte size><TAB><lasting full path><LF>` (`DawWorker::appendSavedLog`; opened, appended and closed per line). Writers: `registerTake` after the worker's first copy and `ensureStableCopies` after a retry (both through `noteSaved`, outside `takesLock`), including adopted takes copied into `recovered_<session>/`. `readSavedLog` ignores blank and malformed lines. A line that could not be written only means "not proven saved".
- Cleanup: `DawWorker::cleanupStaleTemp` runs on the saver thread at its start, before adoption. It deletes a `session_*` folder only when all three hold: (1) the newest content file in it is older than 24 h (`owner.lock`, `saved.log` and the marker are not content, `isBookkeepingName`; with no content the folder's own time, read before the lock file may be created); (2) its lock could be acquired, which is kept for the delete; a `Busy` folder is counted in `cleanupLockedSkips` and left alone, a `Failed` one is left alone; (3) `DawWorker::holdsUnsavedTake` is false. That function is true for: a `*.wav` directly in the folder that is not a capture, is not empty and has no `saved.log` line with its name and size (this includes take files of earlier builds); a non-empty `*.wav.part` that `DawWorker::isTakePart` accepts (see "Takes in a `.part` file" below) and that has no `saved.log` line of its size under its own name or its `.wav` name; a file listed by the marker that exists, is not empty and is not in `saved.log`; a marker with an unknown header or with a path that leaves the folder. A zero-byte file and a `.part` that `isTakePart` rejects are not takes. So age never deletes a take that is not proven saved, with or without a marker, and a folder whose lasting root stays unwritable is kept without a size limit. Age cleanup honours the keep guard too (W4): with `keepGuard` on, a folder that fails `adoptedFolderSafeToRemove` (an unknown file, an unknown subfolder or a cut-short `.part`) is kept and logged once, like in `finishAdoptedFolders`. The destructor still keeps its own temp folder while the marker is there.
- Two acquire modes (lock test group B1). `tryAcquire (folder)` is the owner mode: only the instance that owns the folder calls it (constructor, `retrySessionLock`), and it is the only call that creates `owner.lock` (`OPEN_ALWAYS` / `O_CREAT`). `tryAcquireExisting (folder)` is the mode of the rescue and the cleanup: it opens the file only when it is already there (`OPEN_EXISTING`, `open` without `O_CREAT`) and returns the fourth result `NoLockFile` when it is not, creating nothing. So the presence of `owner.lock` in a folder means "made by a build that locks", and only for such a folder does `Held` prove a dead owner. The statements above and below that the cleanup or the rescue "acquire" a lock mean `tryAcquireExisting`; neither creates a lock file in a folder of someone else.
- Folders without `owner.lock` (an earlier build, or an instance that runs lockless): nobody can prove their owner is dead. Rule table, as implemented in `adoptDeadFolders` and `cleanupStaleTemp` (age = `DawWorker::newestContentTime`, the one helper both use; 24 h = `DawWorker::staleAgeMs`):

  | owner.lock | marker | newest content | rescue | cleanup |
  |---|---|---|---|---|
  | present, `Busy` | any | any | skipped (`rescueLockedSkips`) | skipped (`cleanupLockedSkips`) |
  | present, `Held` | listed, empty or none | any | listed takes, plus the sweep of every unlisted non-empty `*.wav` and every complete unlisted `*.wav.part`; `saved.log` lines; marker removed | under 24 h: kept. Over: deleted when `holdsUnsavedTake` is false |
  | absent | listed | any | the listed takes only (a listed `.wav` that is missing is still read from its `.part`); no sweep of unlisted files; `saved.log` lines for what was copied; marker removed. No `owner.lock` is created | as the row below |
  | absent | empty | any | every `*.wav` except captures (the rule before the lock); no unlisted `.part` by its header; marker removed | as the row below |
  | absent | none | under 24 h | nothing: no copy, no file written into it, nothing counted or reported | kept |
  | absent | none | over 24 h | treated as dead: swept like a `Held` folder, without creating `owner.lock` | deleted when `holdsUnsavedTake` is false, without creating `owner.lock` |

  The saver runs the cleanup first and the rescue second; an aged folder without a lock that holds an unsaved take is kept by the cleanup (`holdsUnsavedTake`) and swept by the rescue of the same start, and removed by a later cleanup. A marked folder without a lock can still be rescued from while an earlier build that owns it is running: that is the behaviour before the lock and is accepted. After its marker is removed its unlisted takes follow the "none" rows. Compatibility: a crash folder of an earlier build with no marker is recovered once it is 24 h old, not at the next start; with a marker, at the next start. Folders without a lock have no lock to hold during a rescue, so `legacyRescueLock` (one mutex per process, `try_lock`) lets one rescuer per process work on such folders at a time; two processes can still both copy from one (the second finds the first copy by name and size, or publishes `name_2`).
- Lockless instance of this build: when the constructor's `tryAcquire` returns `Failed`, or four names in a row were `Busy` (a fifth, fresh name is then used without a lock), the session folder is put in a process-wide registry (`DawWorker::setLocklessFolder` / `isLocklessFolder`). The rescue and the cleanup of every instance in the same process skip a registered folder whatever its marker and age. Another process cannot see the registry; for it the folder follows the table (rows "absent"), which is the accepted residue. `retrySessionLock` runs on the saver thread at each of its existing wake-ups (every `retryBaseMs` and on `requestSaveRetry()`; no timer of its own) and calls the owner-mode `tryAcquire` until it returns `Held`; then the folder leaves the registry and one log line is written. `holdsSessionLock()` reads an atomic copy of the state. The destructor removes the folder from the registry.
- Zero-byte files (review item B2). In the rescue loop a source of 0 bytes (a listed file, a `*.wav` under an empty marker, a `.part` standing in for a missing listed `.wav`) is skipped: it does not stop the loop, does not keep the marker, and one log line per file per pass names it (`DawWorker::zeroByteSkips` counts them). `holdsUnsavedTake` never counted a zero-byte file, so the two agree: such a file never keeps a folder, a real take after it does until it is rescued and logged. In the worker a download is complete only when the request returned 200 and the `.part` exists with more than 0 bytes; a 200 with an empty or missing file deletes the `.part`, records no take, and the job fails with `take <n>: download incomplete`, the message of every incomplete download.

- Retry: the `TakeSaver` thread (one per processor, started in the constructor) calls `ensureStableCopies` every `retryBaseMs` (10 s) while a take is unsaved, doubling the wait after each failed pass up to `retryMaxMs` (60 s). A new failure restarts the schedule; `requestSaveRetry()` runs a pass at once. No retry runs on the message thread.
- Threads: the worker (`DawWorker`) downloads, records the take, renames the `.part` and wakes the saver; its file calls are all in the temp session folder. The saver thread (`TakeSaver`) is the only thread that works on the lasting root: cleanup and adoption at its start, every lasting copy, `saved.log`. Its loop waits until the next retry time or a `notify()`. `takeRecorded` (a new take) makes it run `ensureStableCopies (true)` at once: only takes with `copyFailed` false, so a new take is not held up by the retry of older failures; a first attempt that fails sets the interval back to `retryBaseMs`. `retryNow` (`requestSaveRetry`, the Retry save button) makes it run the adoption pass and a full copy pass. When the retry time is reached it runs a full pass and doubles the interval up to `retryMaxMs` while takes are left (10 s to 60 s). A notify that arrives during a pass is kept by the thread's event, so the next wait returns at once. On a disk that answers a take is saved one thread wake-up plus one copy after its download; the 10 s interval applies only after a failed attempt. The message thread reads `getTakes()` and `getSaveNotice()` (no disk IO in either); the editor makes no file call when it refreshes the grid (see "Editor and the file system"). Removed with the worker's copy: `copyLock`, `lockCopy`, `beginCopyAttempt` (its closing check, counters and test delay are now `countCopyAttempt`, no lock), `copyLockWaiting`, `TakeEntry::copyPending`, `TakeSaver::newFailure`. Teeth switches can still put a copy on another thread (`testWorkerCopies`, `shutdownGuard` off, `unsavedGuard` off, `takeStore` off); nothing serialises the copies then, `copyUnique` picks names atomically and `ensureStableCopies` drops a duplicate. A test that calls `ensureStableCopies` or `adoptDeadFolders` from its own thread is such a second caller too.
- Close: the destructor (1) sets `shuttingDown`, signals the saver thread and the worker (`DawWorker::signalStop`: exit flag, cancel of the request in flight, notify), (2) waits for the collection pool (up to 20 s), (3) `daw.stop()`, (4) cancels the file call the saver has in flight inside `ExclusiveFile` every 50 ms until the saver thread has ended (`saverIo.cancelInFlight()`, see "Cancel at close" below), then `stopThread (-1)`, (5) decides for its temp folder from memory: the folder is kept when the take list has an entry in it with an empty `stable`, or when its legacy marker file exists; otherwise it is emptied and removed (`removeLockedFolder`), (6) releases `owner.lock`. A starred take counts as saved when its entry has `stable` set (written by the saver after a verified copy); nothing is probed. File calls the destructor makes on its own thread, all in the temp session folder: `isDirectory` on the folder and `existsAsFile` on the legacy marker in (5), the listing and deletes of `removeLockedFolder`, and the close and delete of `owner.lock`. It makes none on the lasting root and none under `takesLock`. It runs no copy pass. Once `shuttingDown` is set the saver starts no lasting copy: `ensureStableCopies` checks it between takes and returns the rest as missing, and `countCopyAttempt` (called by `copyStable` and by the rescue) refuses. A copy that is already running stops before its next file call: `copyStable` and the rescue pass `closingNow()` (`shutdownGuard && shuttingDown`) as the abort predicate to `StableTakes::copyInto`, and `ExclusiveFile::copyUnique` / `ensureFolder` read it before every blocking step. The byte copy stops at its next chunk and the other file calls of `copyUnique` / `ensureFolder` are cancelled from the destructor (see "Cancel at close" below for what the close can still wait for). Only the saver thread can be in a file call on the lasting root (an attempt is 22 blocking steps for a new session folder six levels below an existing one, measured by `testCopyAbort`). A file call in flight is not interrupted. An aborted copy returns no file and `CopyResult::Aborted`: `ensureStableCopies` counts that take and the rest as missing and stops without setting `copyFailed`, and the adoption pass leaves the folder for the next start. The wait for the saver thread has no time limit on purpose: JUCE force-kills a thread that misses a `stopThread` timeout, possibly inside a file call. The worker has a limit (`DawWorker::stop`, `kSubmitTimeoutMs + 15000` = 135 s); its file calls (the download, the duration read, the rename) are in the temp session folder, so a lasting root that does not answer cannot hold it. The cleanup pass at the saver's start has no closing check.

**Lasting copies never replace a file.** Two things keep two plugin instances from writing over each other's takes.

- Session folder per instance: `sessionName` is `session_<YYYY-MM-DD_HH-MM-SS>_<6 hex>`, for example `session_2026-10-06_02-04-38_53a120`. The time has one-second resolution, so two instances made in the same second (a project load) used to share one lasting folder; the token (`ExclusiveFile::uniqueToken`: random value mixed with the process id, call counter in the last two characters) makes the name differ. Every consumer matches the `session_` prefix or the `session_*` glob only, and the rescue builds `recovered_<folder name>` from the whole name.
- Exclusive publish: `StableTakes::copyInto` calls `ExclusiveFile::copyUnique` (`source/ExclusiveFile.h/.cpp`). It copies the source to `<name>.<12 hex>.part` in the destination folder, checks that the partial file has the size of the source, then renames it with `ExclusiveFile::moveNoReplace`. When the rename is refused because the name was taken in the meantime, it tries the next free name (`name_2`, `name_3`, ...; at most 50 refused renames). On failure it deletes only its own `.part` file. It returns the file it published, which may carry a `_N` suffix, as `uniqueFile` did before. Abort predicate: `copyUnique`, `ensureFolder` and `StableTakes::copyInto` take an optional `ExclusiveFile::AbortFn` (`std::function<bool()>`, empty = never abort), and `copyUnique` / `copyInto` an optional `CopyResult*` out-parameter: `Copied`, `Failed` or `Aborted`. The predicate is read before every blocking step: the source probe, every folder probe and folder create, the source size read, the `.part` probe, the copy, the size check, every name probe and every rename. When it reads true the call makes no further step, deletes its own `.part` file if the copy step had started (one delete call), returns no file and sets `Aborted`. The byte copy reads the predicate too, once per chunk (see "Cancel at close" below). A failure seen while the predicate reads true is reported as `Aborted`.
- `moveNoReplace` is `MoveFileW` with no `MOVEFILE_REPLACE_EXISTING` on Windows and `link` followed by `unlink` elsewhere. Both fail when the target exists and leave it untouched. Source and target must be on the same volume, which holds because the partial file is made in the destination folder.
- Do not replace this with the public JUCE calls. `juce::File::copyFileTo` is `exists() && deleteFile()` then `copyInternal` (`juce_File.cpp:317-321`), and `copyInternal` on Windows is `CopyFile` with `failIfExists = false` (`native/juce_Files_windows.cpp`, about line 360). `juce::File::moveFileTo` also deletes an existing target first (`juce_File.cpp:300-315`). Only the private `moveInternal` (plain `MoveFile`) refuses an existing target, and it cannot be called from plugin code. `copyFileTo` is used only to write the `.part` file, whose name is new.
- `ExclusiveFile::ensureFolder` creates the destination folder. `juce::File::createDirectory` returns an error to the writer that loses the race for the folder or one of its parents, without creating the levels below; `ensureFolder` does not call it. A try is repeated (at most 8 tries) only when a create failed because its parent was missing (`ERROR_PATH_NOT_FOUND` / `ENOENT`: another writer removed it, or it was not made yet); any other create error (access denied, a share that does not answer) ends the call at once with failure, so a hard failure costs one set of probes and one create, not eight. Per try it probes the folder once with `isDirectory()`; when it is missing it probes the parents upwards until one exists and creates the missing levels top down with one native call each (`CreateDirectoryW` / `mkdir`), accepting a level that another writer made in the meantime. A level whose name is taken by a file ends the call at once. The abort predicate is read before every probe and every create, so once it is true there is no further try.
- Cancel at close. Three things make the saver return at close without finishing its copy.
  - The byte copy. `copyToNew` is `CopyFileExW` with `COPY_FILE_FAIL_IF_EXISTS` and a progress routine that reads the abort predicate and returns `PROGRESS_CANCEL` when it is true. Windows calls the routine once before the first byte and then after every chunk of about 1 MB (measured on NTFS: 2 calls for 4 KB, 64 KB and 1 MB, 3 for 2 MB, 9 for 8 MB, 65 for 64 MB). A cancelled `CopyFileExW` fails with `ERROR_REQUEST_ABORTED` (1235) and has deleted its own partial destination (measured for all those sizes, cancelled at the first and at the second call), so `copyUnique` makes no delete call after it and reports `Aborted`. Elsewhere (not built here): an `O_EXCL` create and a loop of 256 KB chunks that reads the predicate before each chunk and unlinks its own file when cancelled.
  - The other file calls of `copyUnique` and `ensureFolder` (probes, creates, the rename, the delete of the `.part`). `ExclusiveFile::IoCanceller`: the saver thread attaches at the start of `TakeSaver::run` (it duplicates a handle to itself with `THREAD_TERMINATE` access) and detaches before it ends. `step()` marks the thread "in a call" after the abort check and the next `step()` or the function's return unmarks it. The destructor calls `saverIo.cancelInFlight()` every 50 ms while the saver thread is alive; when the thread is marked, that is `CancelSynchronousIo` on its handle, which makes a synchronous file call of that thread fail with `ERROR_OPERATION_ABORTED` (measured on a blocking pipe read: returned at once with 995). The mark and the handle live under one small mutex that is never held across a file call, so a cancel cannot reach a file call the saver makes outside `ExclusiveFile` (markers, `saved.log`, the rescue's reads, the cleanup) and cannot be issued on a thread that has detached. The loop has no cap: it ends when the thread ends, which is the same wait `stopThread (-1)` would make.
  - What a cancelled call does. Every step after it reads the predicate, which is already true, so the call ends as `Aborted`. A cancelled probe reads as "not there"; the next step is never taken, so it cannot lead to a create, a copy or a rename. A cancelled copy (`ERROR_OPERATION_ABORTED`) may leave its `.part`, which is ours: one delete follows. A cancelled rename reports `Aborted` and deletes the `.part`; if the server carried out the rename anyway, the take file exists but is not recorded as saved, and the next start copies it again as `recovered_<session>/<name>` (a duplicate, not a loss). The delete of the `.part` is itself cancellable only after it has run for `IoCanceller::cleanupGraceMs` (1 s); a delete cancelled after that leaves the `.part` file.
  - What the close can still wait for. (1) One chunk of the byte copy (about 1 MB on Windows) before the progress routine is called again. (2) A call inside `ExclusiveFile` that the system does not cancel: `CancelSynchronousIo` only marks the request, the driver decides when it returns, and its effect on a call stuck in the SMB redirector is not tested here; in that case the wait is that one call's system timeout, as before. (3) Up to 1 s for the `.part` delete. (4) One file call the saver has in flight outside `ExclusiveFile`: those are in the temp session folders. Adoption makes no probe of the lasting root; its takes are copied by `ensureStableCopies` like any other take. (5) The age cleanup and adoption stop between folders: `cleanupStaleTemp` takes a `shouldStop` predicate (the saver passes `closingNow()`) that it reads before each session folder and before the capture WAVs, and `adoptDeadFolders` reads `shuttingDown` before each folder; `finishAdoptedFolders` removes nothing once `closingNow()` is true. The folder being worked on is finished first.
  - `.part` cleanup: one native call (`DeleteFileW` / `unlink`) instead of `juce::File::deleteFile` (three calls). When the copy failed because the `.part` name already existed (`ERROR_FILE_EXISTS` / `ERROR_ALREADY_EXISTS`; the file appeared after the probe, or the 48-bit token collided) nothing is deleted, since that file is not this call's; the call reports `Failed` and the saver's next pass uses a new token.
  - Test hooks, all in `ExclusiveFile` unless noted, defaults are the shipped behaviour: `copyCancelEnabled` (true; false = a started copy runs to its end), `testCopyProgressHook` (null; `int (*) (int64 done, int64 total)`, called from the progress routine before the predicate is read, may block, non-zero cancels), `testCopiesStarted`, `testCopiesCancelled`, `testCopyProgressCalls`; `ioCancelEnabled` (true; false = `cancelInFlight` does nothing), `testIoCancelCalls`, `testIoCancelHits`; `testCleanupCalls`, `testLegacyPartCleanup` (false; true = three calls); `testPartToken` (null; fixed token for the `.part` name), `testPartExistsFailures`, `testLegacyPartDelete` (false; true = delete after an exists failure); `testCreateFault` (0; 1 hard error, 2 parent missing), `testCreateFaultsLeft` (-1 = all), `testCreateCalls`, `testFolderTries`, `testLegacyFolderRetry` (false; true = 8 tries on any error); `DawWorker::cleanupFoldersVisited`, `DawWorker::cleanupStopCheck` (true; false = `shouldStop` is not read). `testStepHook` runs while the thread is marked "in a call", so a synchronous read a test blocks in there is ended by the destructor's cancel. No test covers these yet.

**The rename after a download.** `DawWorker::publishDownload` renames `<name>.wav.part` to `<name>.wav` with `ExclusiveFile::moveNoReplace`. A rename that fails (a scanner, an indexer or a sync agent holds the file that was just closed) is tried again: `kPublishTries` = 6 tries, with waits of 50, 100, 200, 400 and 750 ms between them (`publishWaitMs`, 1.5 s in all). The waits are sleeps of 10 ms on the worker thread; each reads the caller's stop predicate (`closingNow()` in `registerTake`, `threadShouldExit()` in the worker) and the function returns false as soon as it is true. `publishDownload` never deletes the `.part` file; the only deletes of a `.part` are the worker's for a download that was cut short, was not a 200 or is incomplete.

When every try failed (or the plugin began to close), the take stays recorded with the `.part` file as its temp file. `registerTake` sets `TakeEntry::temp` to the `.part`, keeps `TakeEntry::name` (the `.wav` name), and tells the worker with `DawWorker::notePartKept` so it does not run the retries a second time. The worker replaces the job's `takeFiles` entry by the `.part` and does not fail the job. The lasting copy is made from the `.part` to `<name>.wav` in the stable folder, at once or by the saver thread's retries. There is no later rename: the take stays on the `.part` for the rest of the session. After a crash, `adoptDeadFolders` adopts a complete `.wav.part` like a WAV and the saver copies it to `recovered_<session>/<name>.wav` (a lasting name that ends in `.part` has that ending removed). What reads the temp file or its name: `AuditionEngine::loadTake` and `fillTakeMetadata` open a `.part` as a stream (the name has no audio extension); `isStarred`, `setStarred` and `trimTakesLocked` use `DawWorker::takeNameOf`, the file name without a trailing `.part`, so a star stays on the take when it gets its lasting file; the Export WAV dialog proposes that name too. In the Takes grid the cell of such a take, while it has no lasting file, shows the file name `<name>.wav`. Whether a `.part` is complete is decided by the header rule in the next section.

**Takes in a `.part` file: order, invariant, rescue.** `registerTake` order (worker thread): (1) the entry is built from the job with `fillTakeMetadata (e, job, i, false)`, which opens no file (the length is the requested one for now); (2) the entry is pushed under `takesLock`; (3) `readTakeDuration` reads the length from the `.part` outside `takesLock` and writes `durationS` to the entry under the lock; (4) `publishDownload` renames the `.part`; (5) the lasting copy and the `saved.log` line. Readers of the metadata before step 3 (`getTakes()` for the grid, `addTakeToCollection`, which needs a lasting file and so runs after step 5) see every field set, with the requested length instead of the measured one. Invariant: from the moment a download is complete, the take is in the take list (step 2) and its bytes are under `<name>.wav` or `<name>.wav.part`; a legacy marker line from an earlier build also names it, and the adoption pass at the next start finds it by either path.

The worker's download step (`DawWorker::stepJob`): `request()` returns 200 with the file only when the download ran to its end (all bytes of `Content-Length` written and no exit seen up to its last check). Such a `.part` is recorded through `onTakeDownloaded` even when the thread's exit is signalled right after; `registerTake` then records it, lists it, tries the rename once and does not copy while closing. Only a download that was cut off, was not a 200 or is incomplete has its `.part` deleted. The kept-part slot (`notePartKept`) is cleared before each call of `onTakeDownloaded`. In `publishDownload`, a rename that reports failure while the `.part` is gone ends the tries and returns whether the take file exists.

Completeness rule: `ExclusiveFile::isCompleteWav (file)` is true when the file has `RIFF` at 0 and `WAVE` at 8, the RIFF size field (bytes 4 to 7, little-endian) plus 8 equals the file size, and a `data` chunk of more than 0 bytes ends inside the file. It reads 12 bytes and up to 64 chunk headers, no audio, and does not use the audio format manager. Why the header can be trusted: the HOT-Step facade converts each take with ffmpeg into a file on disk (`convertOnce`, `ffmpegArgs` with `-c:a pcm_f32le`, server/src/services/daw/dawFacade.ts), renames it when ffmpeg has ended, and the route streams that file with its size as `Content-Length` (server/src/routes/dawV1.ts, `/jobs/:id/audio`). ffmpeg writes final sizes into a seekable output: a file made with those arguments (ffmpeg 8.0.1) had 192,092 bytes, RIFF size 192,084, and the chunks `fmt ` (18 bytes), `fact`, `LIST` and `data`, so the `data` chunk is not at a fixed offset and the chunks are walked. The contract stub (server/scripts/daw-contract-stub.mjs) writes `36 + data` into the RIFF size. A download that stops early has a RIFF size larger than the file and fails the rule.

`DawWorker::isTakePart (part, listed)` is the one predicate for "this `*.wav.part` holds a complete take", used by `adoptDeadFolders` and by `holdsUnsavedTake`: the file has bytes and (a) the marker lists it by its own path, or (b) the marker lists the `.wav` it was to become and that file does not exist, or (c) `isCompleteWav` is true. ## Editor and the file system

The editor runs on the host's message thread. Its VBlank tick (`HotStepLinkEditor::tick`, the part marked `periodic` runs on every 10th tick, about 6 times a second) and its paint code make no file-system call. A folder that answers slowly or not at all (the stable folder on a network drive) therefore cannot stall the host through the refresh.

**What the tick reads.** `refreshTakes` calls `proc.getTakes()` (a copy of the take list under `takesLock`, no file call), `getSaveNotice()`, `isStarred` (a ValueTree lookup) and `audition.getSelected()` (a path), and hands them to `TakeGrid::build` (PluginProcessor.h/.cpp, no GUI types). `build` returns one `TakeGrid::Cell` per take entry: `saved` is `stable` being set, `badge` is `copyFailed` with no `stable`, `pending` is neither, `dragAllowed` equals `saved`, `selected` is the audition selection being equal to the entry's `temp` or `stable` path, `shown` is the queue-card filter. Nothing is stat-ed: a take that is listed has a cell. A lasting file that was deleted or moved by hand after its verified copy still has its cell; the error shows when the take is used (see below). `refreshJob` and `getSourceStateText` use `sourceLoaded()` (a source clip was loaded: length and path, no stat) instead of `sourceReady()`; `prepareSourceJob` still checks the file when Generate is clicked and its "Blocked" text is also held in the Collection footer. `refreshQueue`, `refreshServerStatus`, `refreshCollectionPanel` (cached list, picked up by a generation counter; the scan is a pool job) and `refreshPreview` (peaks fetched only when the selection or `peaksGeneration` changes) read memory only. The preview card and the Export WAV button take "a take is selected" from the selection being non-empty.

**Cell key.** A cell is keyed by `TakeGrid::keyOf (entry)`: `TakeEntry::name`, the take's file name, which is the same in the temp session folder and in the stable folder (for an entry without a name, `DawWorker::takeNameOf (temp)`). `TakeListComponent::setTakes` changes its cell list only when the list of keys changes, and then keeps every cell whose key is still listed. A take therefore keeps its component, its highlight, its star and its waveform when its lasting copy lands. Cells report clicks by key; the editor looks the entry up at that moment (`buildTakeModel().find (key)`) and acts on `Cell::file`: the lasting copy when the take is saved, else the temp file. Export WAV maps the selection to its take the same way, so a take selected before its copy landed is exported from the lasting copy.

**File calls left on the message thread**, each started by a user action or a one-off event, counted per trigger in `EditorFs::testCalls`:

- A new cell: `AudioThumbnail::setSource` in the `TakeCell` constructor opens the take's file to read its header (`tagCell`). Once per cell, not per tick, but it is reached from `refreshTakes` when a take first appears and when the editor is opened (one open per shown take; for a saved take that is the lasting file). Not moved off the thread in this round.
- Click on a take: one `existsAsFile` on its file (`tagSelect`); when the file is gone the take is not selected and the Collection footer says so for 8 s. `AuditionEngine::select` then makes its own `existsAsFile`.
- Export WAV: the file chooser, then `copyFileTo` (`tagExport`); after a failed copy one `existsAsFile` on the source to name the reason, shown in the job label and held in the Collection footer for 8 s.
- Dragging a take: one check per gesture (`TakeCell::dragFileUsable`, `tagDrag`: `existsAsFile` and a size over 0). The lasting path comes from the entry (`dragFileFor`), asked once per gesture; a take with no `stable` is refused with the painted reason and no file call. A lasting file that was removed by hand or has 0 bytes is refused too, and the cell reads `File is missing or empty: cannot be dragged to the DAW.` until the mouse is released (before 2026-10-10 it was handed to the host as it was).
- Dragging a Collection row: one `existsAsFile` per gesture (`CollectionRow::checkDragFile`, `tagDrag`; before round 6 a missing file was probed again on every mouse move).
- "+" on a take, star and remove in the Collection, preset save / load / delete, Drop WAV: the processor's own file work, on the click.
- A finished capture: `pollCapture` (on the tick, once per capture) stops the capture and reads the new file in the temp session folder.
- Standalone start with `HSLINK_PREVIEW_WAV` set: one `existsAsFile` in the constructor.

The Collection is a user-curated library of saved takes, global across projects and plugin instances. This is the storage layer only; there is no panel yet. Code: `source/CollectionStore.h/.cpp`, plus the processor wrappers in `PluginProcessor`.

**Folder.** `Documents/MDMAchine/HOT-STEP LINK/collection`, flat. An item is `<base>.wav` plus the sidecar `<base>.json`. `add` copies the take's lasting WAV under a sanitized name (`sanitizePresetName`) and never overwrites: a taken base name (WAV or sidecar) gets `_2`, `_3`, so adding the same take twice makes two items. The sidecar is written to `<base>.json.tmp` and then moved into place; if that fails the copied WAV is removed again.

**Sidecar fields.** `schema` (1), `name` (display name; rename changes only this, never the file), `caption`, `backend` (`sa3`, `yue2`, `ace`, or `auto` when no backend was requested; the server does not report which backend an Auto job ran on), `model` (server `dit_model`, may be empty), `bpm`, `key`, `seed` (-1 = random), `duration_s`, `mode`, `created` and `added` (ISO 8601 with milliseconds), `starred`, `tags` (array of strings, always written, empty for now), `source` (the lasting file name it was copied from). Unknown fields are ignored and a higher `schema` is read best-effort.

**Listing.** `list()` scans the folder, newest `added` first. A WAV with a missing or unparseable sidecar is still listed with `sidecarMissing` set, its name from the file name and its duration from the WAV header; `list()` never writes or deletes. A sidecar with no WAV is ignored and left alone. `setStarred` / `rename` create a sidecar for a WAV that has none, and refuse (and leave alone) one that exists but does not parse.

**Remove.** `remove()` uses `moveToDeletedFolder` (see Deleted folder above) for the WAV and then the sidecar, so both go to `<root>/Deleted`; nothing is deleted. A `kept` WAV returns false with an error and the item stays listed; `alreadyGone` counts as removed; a `kept` sidecar returns false with the WAV already moved. The WAV and the sidecar are named independently, so after a name clash their numbers in `Deleted` can differ. `list()` reads `*.wav` directly in the root only, so nothing in `Deleted` is listed. It refuses anything that is not a `.wav` whose parent directory is exactly the collection root, so `root/../x.wav` and `root/sub/x.wav` are both refused. Since o120 the notes come from `CollectionStore::removeNoteText (RemoveNote)` and the footer line from the pure `removeResultText (name, removed, note)`; the collection subset checks the exact texts in 7c. A WAV that read `alreadyGone` with a kept sidecar gets its own note (`infoLeftAudioGone`), which has no test of the state itself, only of the text.

**Take metadata.** `TakeEntry` (`HslinkTakeEntry` in `CollectionStore.h`) carries caption, backend, model, bpm, key, seed, duration, mode and creation time, filled once in `registerTake` by `fillTakeMetadata`. Seed is the server's per-take seed, else the requested seed, else -1. Duration is read from the downloaded file's header, else the requested duration.

**Processor API.** `addTakeToCollection (stableFile)`, `getCollection()` (cached list), `getCollectionGeneration()` (bumps on every rescan: add, remove, star, rename, refresh), `refreshCollection()`, `setCollectionStarred`, `renameCollectionItem`, `removeFromCollection`, and the pure `CollectionStore::filter (items, query)`. The cache is empty until the first `refreshCollection()`; nothing scans in the constructor, `prepareToPlay` or on the audio thread.

**Threading.** Message or worker thread only. The store serialises its IO with its own mutex. Never call it while holding `takesLock`, `DawWorker::lock` or the audition lock: copy the take out first, release, then call.

**Test hook.** `setCollectionRoot (dir)` on the processor (`CollectionStore::setRoot`), like `setPresetFolder` and `setStableRoot`. `HSLINK_Tests collection` runs everything in `collection_test` under the test temp folder and removes that folder itself. The removed test item (one WAV and its sidecar) is moved to `collection_test/root/Deleted`, inside that folder, and one check asks for exactly that: `Deleted` did not exist before, holds 2 entries after, the WAV (480104 bytes) and the sidecar (374 bytes) with the sizes they had (66 checks in the subset; under mutant m2 of the Deleted folder test this check fails with 0 entries). The subset does not reach the OS Recycle Bin.

**Teeth.** Runtime env var, same binary: `HSLINK_TEETH=NO_COLLECTION` turns the store calls and the take metadata into no-ops and makes `filter` return its input; every check except the injected-root and cleanup ones must fail. `HSLINK_TEETH=NO_ROOT_GUARD` turns off the inside-the-root check of `remove()`; the three outside-the-root checks must fail (the throwaway files are moved to a `Deleted` folder beside them, in the test's own temp area; not rerun since the change to the Deleted folder).

## DawWorker timeouts

Seven constants govern all HTTP calls:

| Constant | Value | Applies to |
|---|---|---|
| `kRequestTimeoutMs` | 2500 ms | Connect and heartbeat |
| `kSubmitTimeoutMs` | 120 000 ms | generate and understand (may upload a large WAV) |
| `kStallTimeoutMs` | 15 000 ms | Audio downloads: fail if no bytes arrive for 15 s |
| `kJobTimeoutMs` | 15 000 ms | Job polls, cancel and other non-submit calls; also the timeout when split timeouts are off |
| `kHeartbeatMs` | 3000 ms | Interval between status polls |
| `kOfflineAfterMs` | 10 000 ms | Declare offline if no good response in this window |
| `kOfflineAfterFailures` | 3 | Also declare offline after this many failed heartbeats in a row |

On Windows, `WinINet` enforces its own timeout floor around 8 seconds regardless of what the application requests. The `kRequestTimeoutMs` of 2.5 s is therefore a soft request on Windows; the worker's own deadline clock (`deadlineEnabled`) is the real guard for the 10-second offline limit.

Proof of life: a parsed heartbeat, or any other request that returns from `DawWorker::request()` complete with HTTP 2xx (job poll, submit, cancel, backend call, take download; a download that came up short does not count). Each sets `lastOkMs` and clears `consecutiveFailures` under `DawWorker::lock` (`noteServerOkLocked`). It does not raise `heartbeatsOk`, so the worker still needs one parsed status before it is ever online. A failed request that is not a heartbeat does not count as a failure. Worst case from a real outage to offline: 10 000 ms after the last good response (the deadline, read on our own clock in `getSnapshot`); with a server that refuses at once it is the third failed heartbeat, 6 to 9 s after the outage. One request that itself runs longer than 10 s (a slow submit, a backend switch) still holds the single worker past the deadline. Test seams, defaulting to the constants: `offlineAfterMs`, `offlineAfterFailures`, the two extra arguments of `computeOnline`, and the teeth hook `anyResponseIsLife` (false = only a heartbeat counts).

## Build and deploy

Build with `build.bat` (or `cmake --build build --config Release`), then deploy with the script. These are two steps on purpose.

```bat
build.bat
powershell -File tools\deploy.ps1 -DryRun
powershell -File tools\deploy.ps1
```

- **`COPY_PLUGIN_AFTER_BUILD` stays `FALSE`** in `CMakeLists.txt`. A build must never write into a plugin folder a host may have open, and a test build must never replace the plugin in the host by accident.
- **One deploy target.** `tools\deploy.ps1` copies the VST3 bundle to `<Dest>\VST3\HOT-STEP LINK.vst3` (whole bundle folder) and the Standalone exe to `<Dest>\Standalone\HOT-STEP LINK.exe`. The default `-Dest` is the maintainer's plugin folder, `<plugin folder>`; on another machine pass `-Dest <your folder>`. `-Config` picks the build configuration (default `Release`).
- **No CLAP.** `FORMATS` is `VST3 Standalone`, so the script writes nothing to `<Dest>\CLAP`.
- **Never the Common Files path.** The script refuses any destination under Program Files (exit 2), which includes `C:\Program Files\Common Files\VST3`. On the maintainer's machine `C:\Program Files\Common Files\VST3\MDMAchine` is a link to the same `VST3` folder; deploy to the real folder and leave the link alone.
- **Locked files.** Before it copies anything, the script tries to open every existing destination file for exclusive write. If one is open in a DAW or in the Standalone app, it lists the locked files, copies nothing and exits 3. Close the host and run it again. The script never forces a copy and never stops a process.
- **Stale artefacts.** The script warns when an artefact is older than the last commit that touched `source/` or `CMakeLists.txt`. It still copies; treat the warning as "rebuild first".
- **No deletes.** An existing bundle is replaced file by file. A file that a newer build no longer produces would stay in the destination bundle; remove it by hand if that ever happens.
- **What it prints.** The git short hash of HEAD, then for each file the path, size, LastWriteTime and plugin version (from the binary's version resource, and from `moduleinfo.json` for that file).
- **Exit codes.** 0 ok, 1 missing artefact, 2 refused destination, 3 locked destination file, 4 copy failed.
- **Stale clap-juce-extensions deps.** Commit 25f224c merged the two clap-juce-extensions patches into `cmake/patches/clap-juce-extensions-state.patch`. A build dir whose deps were fetched and patched before 25f224c fails at `cmake/patches/apply_git_patch.cmake:129-130` on configure. Recycle `build/_deps/clap-juce-extensions-*` once and reconfigure.

The destination folder on the maintainer's machine is inside the MDMAchine_VST git repository and is not ignored there, so the deployed files show up as untracked in that repository. Do not commit them from a HOT-STEP LINK session.

To validate the deployed bundle, run pluginval on the deployed path, not on the build tree:

```bat
pluginval.exe --strictness-level 5 --validate-in-process --validate "<plugin folder>\VST3\HOT-STEP LINK.vst3"
```

## Test target

The `HSLINK_Tests` console app covers:

- **R1b**: host sync. A fake `AudioPlayHead` at 97 BPM 7/8 is driven for 100 blocks at 48 kHz / 512. The test verifies BPM, numerator, denominator, PPQ advance, loop points, and the update counter.
  - Loop BARS display convention: the end bar is `barOf (loopEnd) - 1`, so a partial final bar is dropped (ppq 8..22 in 4/4 shows "3-5"). This is the accepted convention, pinned by the `syncBarsCellText` checks in `tests/HslinkTests.cpp`.
- **R2a**: capture ring. A 1 kHz sine at 44.1 kHz host rate is pushed for 2 seconds, the ring is stopped, and the output WAV is verified: 48 kHz, float32, 2 channels, length within 1 ms, and the tone within 1 Hz.
- **R3**: DawWorker offline detection. The worker's deadline is shortened and the test verifies it transitions to offline within the expected window.
- **R4**: job submission and state machine, tested against the daw-contract-stub (see below).
- **R5b**: audition level match, resample, transport sync, crossfade, and no-alloc render. The no-alloc test instruments `operator new` to count allocations during `AuditionEngine::render` and checks the count is zero.
- **R6**: stable take naming (`StableTakes::slugify`, `makeName`, `uniqueFile`) and copy.

### HSLINK_TEETH flags

Pass `-DHSLINK_TEETH=<flag>` to CMake when building `HSLINK_Tests` to produce a deliberately broken build. Every test that uses the teeth check must fail on the broken build.

| Flag | What it breaks |
|---|---|
| `BAD_SYNC` | Host sync: wrong field copied, so PPQ does not advance correctly |
| `NO_RESAMPLE` | Capture: LagrangeInterpolator skipped; tone arrives at the wrong frequency |
| `NO_GAIN` | Audition: level-match gain fixed at 1.0 regardless of target |
| `NO_AUD_RESAMPLE` | Audition: take not resampled to host rate |
| `BAD_PPQ` | Audition transport sync: wrong PPQ anchor formula |
| `NO_XFADE` | Audition: crossfade disabled |
| `NO_LOOP_END` | Capture: recording does not stop at the loop end |
| `NO_REGION` | Generate: region not sent in the request JSON |
| `NO_SOURCE_GATE` | Generate: repaint/lego allowed without a source file |
| `KEY_IN_STATE` | Settings: DAW key written to plugin state instead of LINK.settings |
| `BAD_FIELD` | Generate: multipart field name wrong (sends `req` instead of `request`) |

Example: `cmake -B build -DHSLINK_TEETH=NO_RESAMPLE` then `build.bat test` should print a FAIL for the 1 kHz frequency check.

## Running against the daw-contract-stub

The HOT-Step repo ships a lightweight Node stub at `tools/daw-contract-stub/daw-contract-stub.mjs` (or `server/scripts/daw-contract-stub.mjs`, depending on the HOT-Step version). It implements the full `/api/v1/daw` facade contract without needing the C++ engine.

Start it with:

```sh
node daw-contract-stub.mjs --ok
```

Default port is 3001. Pass `--port N` to use a different port.

**Caption modes.** These are not command-line flags: the stub switches behaviour on the `caption` field of the generate request (see the header of `server/scripts/daw-contract-stub.mjs` in HOT-Step-CPP).

- `single`: the job omits `takes_done` (non-sequential, like the facade); only the `takes` array is reported.
- `badid`: generate returns a hostile path-traversal job id; the client must refuse it.
- `slowsubmit`: the generate response arrives after 5 s, for the submit timeout path.
- `slow`: each take streams at 4 KB per 500 ms (about 12 s per take), for shutdown tests.
- `trunc`: take 1 is sent with a Content-Length larger than the body, then the socket closes, for the download-length check.
- `hold`: the job stays running until cancelled; `partial`: the job ends `partial` with half the takes.

**What `--ok` mode provides:**

- `GET /api/v1/daw/status` returns a well-formed status body with `online: true` and a set of ETA estimates.
- `POST /api/v1/daw/generate` accepts any mode and returns a job id. The stub advances the job to `done` on the next poll.
- `GET /api/v1/daw/jobs/:id` returns progress and state.
- `GET /api/v1/daw/jobs/:id/audio` returns a minimal valid float32 WAV.
- `POST /api/v1/daw/jobs/:id/cancel` returns `{ "ok": true }`.
- `POST /api/v1/daw/understand` returns a plausible BPM/key response.

The contract test script (`server/scripts/daw-contract-test.mjs`) runs the full suite against the stub and the real server. Run it with:

```sh
node daw-contract-test.mjs --base http://127.0.0.1:3001
```

### Live backend switch driver (`liveswitch`)

`HSLINK_Tests.exe liveswitch` proves the backend switch against a real HOT-Step, including the server's own `409 backend_mismatch`, which the stub cannot give. It is never part of the default run: it needs the subset argument and `HSLINK_LIVE=1`. Without the variable it prints one SKIP line and sends nothing; when the server does not answer, does not list the wanted backends, or is not idle (`GET /api/generate/queue`), it prints SKIP or STOP, counts no check and exits 0.

```sh
HSLINK_LIVE=1 build/HSLINK_Tests_artefacts/Release/HSLINK_Tests.exe liveswitch
HSLINK_LIVE=1 build/HSLINK_Tests_artefacts/Release/HSLINK_Tests.exe liveswitch sa3 ace
HSLINK_LIVE=1 HSLINK_TEETH=NO_BACKEND_SWITCH build/HSLINK_Tests_artefacts/Release/HSLINK_Tests.exe liveswitch sa3 ace
```

**Arguments.** `liveswitch <from> <to>` with the ids `ace`, `sa3`, `yue2`: the driver first puts the server on `<from>` with its own `POST /api/backends/active` (status printed) and confirms `activeId`, then the worker submits one job with expected backend `<to>`. `<from>` equal to `<to>` is the control row: no switch may be sent. Without arguments `<to>` is `sa3` and `<from>` is whatever is active (`ace` when that is already `sa3`). One row per command; each row ends with one `ROW from=... RESULT=PASS|FAIL|TIMEOUT|NOT RUN` line. The backend that was active before the row is restored at the end of every row.

Matrix measured on 2026-10-07 (5 s, 1 take, GPU0 16 GB): ace to sa3 7.4 s, sa3 to ace 5.5 s, ace to ace 81.8 s (0 switches), yue2 to ace 5.1 s, yue2 to sa3 9.5 s, sa3 to yue2 61.5 s, ace to yue2 61.5 s. The very first ACE job after a server start took longer than the 420 s cap (LM phase 129 s, then cold model loads) and was recorded as TIMEOUT; the same row passed on the second run. Run an ACE row twice before reading a TIMEOUT as a fault.

| Variable | Default | Meaning |
|---|---|---|
| `HSLINK_LIVE` | unset | must be `1` |
| `HSLINK_LIVE_URL` | `http://localhost:3001` | server base URL |
| `HSLINK_LIVE_KEY` | the key stored in `LINK.settings` | sent as `X-DAW-Key`, like the plugin; never printed. A loopback server needs none |
| `HSLINK_LIVE_DURATION_S` | `5` | take length; 5 s is the shortest the plugin's Duration control sends. The server accepts any positive value; YuE2 ignores it and the facade trims the take |
| `HSLINK_LIVE_LIMIT_S` | `420` | time cap for the job; on timeout the job is cancelled through the worker |

**What it does.** A real `DawWorker` (no `testBackendCall`, the real `request()` path) submits one job for `<to>`, 1 take, fixed seed, neutral caption, no lyrics, ACE model on Auto, as `makeRequest()` builds it for that backend choice. `DawJobRequest` has no steps field, so the server's default for the backend applies. The driver prints every `DawJob::label` and `DawJob::headline` the job passes through with ms from the submit, `getSwitchingTo`, `switchesSent`, how long the switch was seen, the server's `activeId` after the submit, the final state, the server job id, and the size and length of the first take. It checks: one switch POST when `<from>` differs from `<to>` and none when they are equal, `activeId` is `<to>` after, every label is one `DawJob::label` can produce with the matching header and nothing after a finished label, and the job ends done or partial with a take of non-zero length. The strict label order is a counted check when `<from>` differs from `<to>`: the collapsed labels must be exactly queued, switching, sending, running, then done or partial, and `sending` must never be seen before `switching` (with `<from>` equal to `<to>` the line is printed as `[informational]`). The driver samples in a tight `Thread::yield` loop until the submit has an answer, so a label that lasts microseconds is seen. Before 2026-10-07 a real server showed queued, sending, switching, sending, running, because `ensureBackend` read `GET /api/backends` before it marked the switch. It now marks the switch first, and `processJobs` sets the same mark in the locked step that picks the job, which closed the last instant of `sending` (measured live 2026-10-07 on `ace sa3`: FAIL with `sending` at 0.0 ms before the `processJobs` mark, PASS after; `sa3 ace` PASS after). The `processJobs` mark is set only for the first job of a pass, because `cancelJob` ends the request in flight for a marked job; a generate job picked in the same pass behind an understand job can still read `sending` until `ensureBackend` runs. The stub side of this is `HSLINK_Tests backend`, cases S-m (slow question, other backend active), S-n (slow question, wanted backend already active: the row still reads `switching` for the length of the question, no POST) and S-p (the job's own mark is empty after each way out). The worker does not expose the HTTP status of its switch POST; the driver reads it from the outcome (`activeId` and the job message). Audio is never played.

**What it changes on the server.** The active backend becomes `<from>`, then `<to>` for the job (the server frees the outgoing backend's weights and loads the new one), one job renders, and at the end, also after a failure or a timeout, the driver posts the original backend to `/api/backends/active` and prints the `activeId` it reads back. The weights the original backend had loaded are not loaded again until its next job. Takes go to the test's own temp folder and are removed. Check GPU headroom first and do not run it while someone is using the server.

**Teeth.** `HSLINK_TEETH=NO_BACKEND_SWITCH` clears `DawWorker::switchBackend`: the submit goes out without a switch, the server answers `409 backend_mismatch`, nothing renders, and the checks for the switch count, the `activeId` and the finished take fail. The driver also sends the same body once more itself and prints the server's raw 409 answer. The label check and the restore check cannot fail under this switch and are regression guards there.

## Take edit (crop and loop)

Code: `source/TakeEdit.h/.cpp` (namespace `TakeEdit`), the same shape as `TakeStretch`: one call reads a WAV and writes another, no GUI, no processor, no globals, never the audio or the message thread. There is no GUI yet. The test group is `edit`, see "Take edit (`edit`)" under Test target.

**Where the edit data lives.** `TakeEdit::EditData` (crop start, crop end, loop start, loop end) is a field of the take entry (`HslinkTakeEntry::edit` in `CollectionStore.h`) and of `CollectionItem`. `CollectionStore::add` copies it from the take, and the sidecar carries it as `crop_start`, `crop_end`, `loop_start`, `loop_end`, each written only when set, next to the tempo keys in `toJson` / `fromJson`. It is never written into the audio file: the take's WAV stays as it was downloaded, and a render makes a new file. On load a value that is missing, not a number, negative or absurdly large reads as not set; a crop whose end is not after its start is dropped as a whole, and so is a loop with one point missing (`EditData::sanitized`). The file length is not known to the sidecar reader, so points past the end are clamped at render time.

**Units.** Sample frames of the take's own file at that file's own rate, `int64`, -1 = not set. An end is exclusive. An unset crop start means the file start and an unset crop end the file end. The measured tempo stays in seconds (`downbeat_s`, `first_beat_s`); convert with the file's rate.

**Length rules** (exact to the sample, `EditResult::outSamples`):

- Crop only (`loopRepeats` 0): `used.cropEnd - used.cropStart`. The output is the source between the two points. A cut end inside the file gets a fade of `fadeMs` (default 5, at most half the region); an end at the file's own start or end is left alone. Loop points do not change the audio.
- Loop render (`loopRepeats` N, 1 or more): `N x (used.loopEnd - used.loopStart)`. Only the loop region is rendered. The audio before the loop start and after the loop end is not in the output and the crop points are not used. The last `seamFadeSamples` of every repeat, the last one too, are a crossfade from the end of the loop region into the audio just before the loop start. So each repeat ends on the frame before the loop start and the next begins on the loop start itself; the file has no fade at its own start or end and also loops without a step when played end to end. `seamFadeSamples` is `fadeMs`, limited to the audio that exists before the loop start and to half the loop. A loop that starts at frame 0 has nothing before it and gets a plain cut (`seamFadeSamples` 0).

**Seam law.** The crossfade follows how alike the two overlapped segments are. `r` is their normalised correlation over the fade length, pooled per channel (`a` the loop tail, `b` the audio before the loop start): `r = sum_c (sum (a_c x b_c)) / sqrt (sum_c (sum (a_c x a_c)) x sum_c (sum (b_c x b_c)))`. It is never taken from the channel sum, which cancels on wide or out of phase stereo: with R = -L the sum is silent and read 0, so equal power was chosen and the +3 dB and the clipping came back although each channel ran into its own start (o129). One `r` and one gain for all channels. For the law `r` is limited to 0..1: a negative one counts as 0 and so does a silent segment. With `th = t x pi / 2`, `t` from 0 to 1 over the fade: `out = (tail x cos (th) + before x sin (th)) / sqrt (1 + 2 r cos (th) sin (th))`. `r` 0 is the equal power law, right for two unrelated signals. `r` 1 is an equal gain law (the two gains add up to 1): a well chosen loop, whose end runs into its own start, keeps its level and its peak, where equal power raised the middle of the fade by 3 dB (1.41x) and clipped a hot take in a 16 or 24 bit file. In between the expected power stays flat for the measured `r`, and no gain is above 1. `EditResult::seamCorrelationUsed` has `r`. `EditResult::seamCorrelation` has the signed value before the limit, -1..1, for a later editor screen: near 1 is a loop whose end runs into its start; near 0 means unrelated segments, a silent one, or no crossfade at all (`seamFadeSamples` 0); clearly negative means the loop point is out of phase and the level dips inside the fade (-9.88 dB in the middle of the fade on the opposite phase case of the tests, signed value -0.93). The `loop-check` tool prints both.

**Regions outside the file.** A point past the file end is put at the file end, so a crop or a loop that overlaps the file in part is cut down to the part inside it. A region that is wholly outside is refused and nothing is written (no dest, no temporary file): a crop render fails with `the crop region is outside the file` when a crop start that was given lies at or past the file end or a crop end that was given is 0, and with `the crop region is empty` when both were given and the end is not after the start; a loop render fails with `the loop region is outside the file` when the loop start lies at or past the file end. A render never falls back to the whole file. In a crop render a loop outside the file only reads as not set in `used` (loop points do not change a crop).

**Snapping.** `snapToGrid` needs a usable grid (`TakeEdit::gridUsable`): `gridBpm` inside 30 to 300 and `gridDownbeatSec` finite and not further than `kMaxGridDownbeatSec` (600 s) from the file start, either side. With any other value (NaN, infinite, a zero or huge tempo, a huge downbeat) the snap is skipped, the points are used as given and `EditResult::gridSnapped` is false; the render does not fail for it. The range is wider than the detector's 50 to 220 because the helper also serves a tempo the user types. The loop start and length on the grid are computed in closed form (no stepping loop), so no value can keep the one pool thread busy. `requestTakeEdit` applies the same rule to the take's measured tempo (`gridSkipped`), and the sidecar reader drops a tempo whose number or downbeat is not finite or whose downbeat is out of that range (it only fills a `CollectionItem`; a take entry gets its tempo from the measurement). Crop points that are set go to the nearest beat each. The loop start goes to the nearest beat inside the file and the loop length to the nearest whole number of beats (at least one, fewer when they do not fit). `snapToZeroCrossing` then moves crop points that are set and inside the file to the nearest zero crossing of the channel sum within `zeroCrossingMs` (default 3) on either side; loop points are never moved by it, so a loop keeps its length. `EditResult::used` has the points the render used.

**Bars fit.** `fitBars` with `fitBpm` and `fitBeatsPerBar` reports the nearest whole bar count of the rendered region (`bars`) and `leftoverMs` = region length minus that many bars, signed. Nothing is stretched. To make the region exactly that many bars, render it and then stretch the result with `requestTakeStretch (newTemp, fitBpm x (regionLength - leftover) / regionLength, fitBpm)` (output length = input length x source tempo / target tempo).

**Files.** As the stretch: source read only, dest equal to source refused, an existing dest refused, `.wav` only, 16 bit, 24 bit and 32 bit float only, at most 8 channels and 10 minutes (source and result), rate, channel count and format kept. The audio goes to `<dest>.<token>.editing`, created with `ExclusiveFile::createNew` (the cleanup guard is armed only after that create), and is renamed with `moveNoReplace`; a failure or abort removes the partial file. `TakeEdit::testEditPartToken` (null in the plugin) forces the token. Never throws.

**Processor.** `requestTakeEdit (tempFile, EditData, EditOptions)` stores the points on the take, then runs the render on the stretch pool thread (so never beside a stretch), under the tempo job's gate. With `snapToGrid` the grid is the take's own measured tempo and downbeat when the take is measured and valid; else the grid snap is skipped, which is logged and shown by `getLastTakeEditReport().gridSkipped`. The result is `<stem>_edc<hash>.wav` (crop) or `<stem>_edl<N>x<hash>.wav` (loop) in the take's temp session folder (`editedTakeName`; the hash is 4 hex digits of the request, so the same request twice is refused as an existing name). It is listed as a new unsaved take the way a stretched one is and then measured; it has no edit points of its own, and the asked tempo is kept. The original take keeps its file and gains only the stored points. `setTakeEdit` stores points without rendering. `waitTakeEditIdle` is for tests.

**How a GUI round would call it.** A waveform view with crop and loop handles keeps its handle positions in sample frames of the take's file and calls `setTakeEdit` when a handle is released, so the points survive in the take entry and reach the sidecar when the take is added to the collection. For live snapping while dragging it calls the pure `TakeEdit::snapToGrid` (with the take's `tempo.bpm` and `tempo.downbeatSec`) and `nearestZeroCrossing` on the samples it already holds for the drawing. "Apply crop" is `requestTakeEdit` with `loopRepeats` 0, "Export loop" the same with `loopRepeats` 1 or more; the new take appears in the grid at the next refresh and `getLastTakeEditReport()` (compare `serial`) gives the points used, the bars fit and any error for a status line. Warp markers, when they come, are further per-take data of the same kind (frames of the source file beside the take) and a further render in this unit or beside it; the crop and loop points stay valid because they always refer to the unchanged source file.

## Vendored libraries

`third_party/` holds source taken from other projects, each folder with the upstream `LICENSE.txt` and a `README-VENDORED.txt` (URL, tag, commit, date, files taken). `third_party/.gitattributes` (`* -text`) keeps the files byte-identical to upstream. They are never edited here; their compiler warnings are switched off around the include in `source/TakeStretch.cpp`.

To update: clone the new tag of `signalsmith-stretch` into a scratch folder, read the `GIT_TAG` of `signalsmith-linear` in its `CMakeLists.txt` and clone that tag too, copy only the files listed in each `README-VENDORED.txt` (`signalsmith-stretch.h`; `stft.h`, `fft.h`; both `LICENSE.txt`), then update the commit, tag and date in both README files and in `THIRD_PARTY_NOTICES.md`. Define none of the `SIGNALSMITH_USE_*` macros (they pull in `platform/` headers that are not vendored). Rebuild, then run `stretch-file` in both modes and compare the counts and the measured tempo with the CHANGELOG entry.
